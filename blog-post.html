Why I chose SQLite for TimeFlow

Short write-ups on decisions I made, bugs I fixed, and things I learned while building things and this portfolio. Mostly for future-me, shared in case it's useful to someone else too.

When I started building TimeFlow, the obvious answer for "which database?" felt like SQL Server or PostgreSQL — those are the names you hear most in .NET tutorials. But neither made sense once I actually looked at what TimeFlow is: a desktop app, running on one machine, for one user, with no server to talk to.

What the app actually needed

TimeFlow needed a database that:

  • Works fully offline, with no separate server process to install or run
  • Ships as part of the app itself, so the installer stays simple
  • Is fast enough for one user's data, without needing connection pooling or tuning

SQLite fits all three. It's a single file on disk, the database engine is embedded directly in the app, and Entity Framework Core supports it as a first-class provider — so the data layer looks almost identical to how it would with SQL Server.

What it costs later

The trade-off is real, though. SQLite doesn't handle concurrent writes from multiple processes well, and it has no built-in way to sync data across devices. For a single-user desktop tool that's fine — but it's the reason I wouldn't reach for SQLite if TimeFlow ever became a multi-user or cloud-synced product.

The right database isn't the most "production-grade" one — it's the one that matches what the app is actually doing.

That's the bigger lesson I took from this decision: pick infrastructure for the shape of the problem you have, not the one you might have someday. It's a principle I'm carrying into how I think about the CMS behind this portfolio too.
